# План реализации комментариев и вложений

## Цель и границы

Добавить к задачам неограниченное количество комментариев и файловых вложений. Комментарии поддерживают Markdown. Вложения можно добавлять при создании задачи и при написании комментария к существующей задаче.

Файлы загружаются и сохраняются только после подтверждения формы: создание задачи подтверждает вложения из формы создания, а отправка комментария подтверждает вложения в комментарии. Закрытие или отмена формы не должны сохранять файлы.

## Поведение для пользователя

- В формах создания задачи и создания комментария есть кнопка со значком скрепки; также можно вставить файл из буфера обмена через Ctrl+V.
- До отправки выбранные файлы показаны как черновики, которые можно убрать.
- Новая задача сохраняется вместе с первоначальным комментарием и вложениями; ошибка не должна оставлять частично сохранённые данные.
- Для существующей задачи комментарий и его файлы сохраняются по отправке комментария. Файлы, выбранные в форме редактирования задачи, прикрепляются к комментарию только после подтверждения этого комментария.
- Комментарии отображаются с форматированием Markdown, с переключением между вводом и предпросмотром.
- Изображения показываются миниатюрами и открываются в полном размере.
- Markdown, TXT, CSV, YAML и файлы популярных языков программирования открываются во встроенном предпросмотре. Для кода используется готовая библиотека подсветки синтаксиса.
- Прочие типы файлов показывают имя и действие скачивания; содержимое файла не исполняется.

## Этапы реализации

### 1. Уточнить контракт и зависимости

- Изучить текущие модели задач и комментариев, API, интерфейс и экспорт.
- Выбрать готовые библиотеки Markdown-рендеринга и подсветки кода, совместимые с React и сборкой проекта.
- Установить и задокументировать лимиты размера одного файла, суммарного размера запроса и поддерживаемые форматы.
- Выбрать постоянное файловое хранилище для self-hosted развёртывания и определить его резервное копирование.
- Управлять функциональностью вложений отдельной переменной окружения `MYTODO_ATTACHMENTS_ENABLED` (по умолчанию `false`). При значении `false` интерфейс скрывает элементы добавления/просмотра вложений, а API отклоняет операции с файлами понятной ошибкой недоступности. При включении требуется `MYTODO_ATTACHMENTS_DIR` — абсолютный путь к каталогу хранения внутри backend-контейнера; backend проверяет доступность и права каталога при запуске. Обычные комментарии без файлов остаются доступны.

### 2. Схема данных и файловое хранилище

- Хранить комментарии отдельными записями, связанными с задачей и автором: Markdown-текст и дата создания.
- Хранить метаданные вложений отдельно и связывать их с комментарием: внутренний ключ, исходное имя, MIME-тип, размер и дата.
- Сохранять бинарные данные вне публичной директории; внутренние имена генерировать на сервере.
- Стандартный путь внутри контейнера: `/var/lib/mytodo/attachments`. В production Compose подключать к нему постоянный именованный volume `mytodo_attachments` и передавать `MYTODO_ATTACHMENTS_ENABLED=true` вместе с `MYTODO_ATTACHMENTS_DIR=/var/lib/mytodo/attachments` в backend. Для установки на конкретный диск разрешить bind mount на этот же путь из host-каталога, выбранного администратором.
- Вариант с внешней PostgreSQL также должен подключать этот volume к backend: файловое хранилище принадлежит API-сервису и не зависит от того, где размещена база данных. В dev/test окружениях настроить отдельные каталоги/volumes, чтобы тестовые и пользовательские файлы не смешивались.
- Хранить в БД только метаданные и сгенерированный сервером относительный ключ (например, UUID); не сохранять абсолютные пути. Вычислять путь к файлу только внутри настроенного `MYTODO_ATTACHMENTS_DIR` и проверять, что он остаётся внутри корня хранилища.
- Добавить Drizzle-миграцию и ограничения целостности, включая связь с владельцем данных.
- Предусмотреть очистку метаданных и файлов при удалении комментария, задачи или аккаунта.

### 3. Backend API и безопасное сохранение

- Добавить API чтения комментариев, создания комментария с несколькими файлами и получения вложения по идентификатору.
- Поддержать сохранение задачи с первоначальным комментарием и вложениями в подтверждаемом сценарии создания.
- Проверять авторизацию и владение задачей при каждом чтении и изменении, включая выдачу файла.
- Проверять размер, число файлов, расширение и MIME-тип на сервере; клиентские данные считать недоверенными.
- Для выдачи файлов использовать безопасные заголовки; предпросмотр разрешать только для явно поддержанных типов, остальные отдавать как скачивание.
- Согласовать запись файлов с транзакцией БД: использовать временные файлы и удалять частично записанные данные при ошибке.
- Покрыть API-тестами несколько комментариев и файлов, доступ, ограничения, ошибочные типы и откат/очистку при сбое.

### 4. Интерфейс и черновики файлов

- Создать переиспользуемый компонент выбора файлов для формы создания задачи и формы нового комментария.
- Поддержать скрепку, множественный выбор, Ctrl+V, список черновиков и удаление файла из списка.
- Хранить выбранные файлы только локально до отправки формы; не вызывать сохранение на сервере при выборе или вставке.
- После успеха очищать черновики; при ошибке сохранять текст и выбор файлов для повторной отправки.
- Добавить UI-тесты на выбор, вставку, удаление черновика, подтверждение, отмену и ошибку.

### 5. Markdown и предпросмотр

- Добавить ввод и безопасный предпросмотр Markdown-комментариев.
- Санитизировать отрендеренный контент и блокировать опасные HTML-вставки и URL-схемы.
- Для изображений реализовать миниатюру, открытие полноразмерного файла и состояния загрузки/ошибки.
- Для `.md`, `.txt`, `.csv`, `.yaml` и `.yml` показывать экранированный текстовый предпросмотр.
- Для популярных исходных форматов применить готовую библиотеку подсветки синтаксиса; ограничить размер текста предпросмотра.
- Для прочих форматов показывать метаданные и скачивание.
- Покрыть тестами типы предпросмотра, небезопасное содержимое и состояния ошибок.

### 6. Сквозные сценарии и выпуск

- Добавить Playwright-сценарий создания задачи с изображением и Markdown-файлом и проверить их сохранение после отправки.
- Добавить сценарий Ctrl+V и отправки нескольких комментариев с несколькими файлами.
- Проверить, что отмена формы задачи или комментария не оставляет файлы на сервере.
- Проверить очистку файлов при удалении связанных данных и невозможность прочитать чужое вложение.
- Обновить пользовательскую документацию, лимиты и инструкции по резервному копированию.
- Документировать включение функции через `MYTODO_ATTACHMENTS_ENABLED=true` и `MYTODO_ATTACHMENTS_DIR`, настройку volume или bind mount, права записи для пользователя backend-контейнера и совместное резервное копирование каталога с БД.
- Выполнить проектный цикл проверок: `pnpm test`, `pnpm test:e2e` и `pnpm build`; устранить регрессии перед выпуском.

## Основные риски

- **Неподтверждённая загрузка:** отправлять файлы на сохранение только вместе с явным подтверждением задачи или комментария.
- **XSS через Markdown/файлы:** санитизировать Markdown и никогда не исполнять содержимое вложений.
- **Большие и поддельные файлы:** проверять размер и тип на сервере, не полагаться на MIME, заданный браузером.
- **Файлы и транзакции:** транзакция БД не откатывает файловую систему; нужна компенсационная очистка при сбое.
- **Изоляция пользователей:** авторизацию проверять на каждом запросе чтения файла, а не только при показе задачи.
- **Self-hosted эксплуатация:** подключить хранилище как постоянный volume и включить его в резервные копии.
- **Функция выключена конфигурацией:** если `MYTODO_ATTACHMENTS_ENABLED` отсутствует или равно `false`, вложения скрыты в UI и недоступны через API, при этом комментарии без файлов продолжают работать. При значении `true` обязателен `MYTODO_ATTACHMENTS_DIR`; backend проверяет доступность и права каталога при запуске и завершается с ясной ошибкой при неверной конфигурации.

## Критерии готовности

- К задаче добавляется любое количество комментариев, каждый комментарий может включать несколько вложений.
- Создание задачи и комментария поддерживают скрепку и Ctrl+V.
- Файлы сохраняются только после подтверждения формы; отмена не оставляет серверных файлов.
- Markdown безопасно отображается с предпросмотром; изображения отображаются как картинки.
- Markdown, TXT, CSV, YAML и популярные исходные форматы можно просмотреть, остальные файлы безопасно скачиваются.
- Сервер проверяет доступ, размер и формат файла; удаление связанных данных очищает хранилище.
- Основные сценарии и ошибки покрыты domain/API/UI/E2E-проверками.
