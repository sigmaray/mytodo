# План реализации повторяющихся задач

## Цель и границы

Добавить повторение задач отдельным этапом после MVP. В текущем MVP повторяющиеся задачи прямо исключены из объёма работ; этот документ описывает будущую функциональность и не меняет это ограничение.

Первая версия поддерживает календарные повторы:

- каждый день;
- каждую неделю в выбранный день недели;
- каждый месяц в число месяца.

Сложные правила («каждый второй вторник», рабочие дни, интервалы с несколькими условиями), NLP-парсинг, перенос серии между пользователями и журнал пропущенных экземпляров в первую версию не входят.

## Принятые продуктовые решения для первой версии

- Дата следующего экземпляра вычисляется от **плановой даты** предыдущего экземпляра, а не от даты фактического выполнения. Поэтому просроченная задача не сдвигает всю серию.
- Если месячная дата отсутствует (например, 31 февраля), использовать последний день этого месяца. Следующий экземпляр снова вычисляется от предыдущей плановой даты исходного правила, чтобы короткий месяц не сдвигал серию навсегда.
- После завершения создаётся один следующий экземпляр. Пропущенные даты не порождают пачку задач.
- У каждой задачи серии собственный статус и содержимое. Завершение экземпляра не завершает будущие задачи.
- Удаление незавершённого экземпляра не создаёт следующий. Остановка серии выполняется отдельным действием; она не удаляет уже созданные экземпляры.
- Правило повтора доступно только для задач с датой выполнения. Без даты выбрать повтор нельзя.

## Этапы реализации

### 1. Зафиксировать контракт и модель серии

- Уточнить UX текста правила: как показывать недельный день и месячное число, как редактировать и останавливать серию.
- Представить правило типом с дискриминируемым объединением: `daily`, `weekly` с днём недели, `monthly` с числом месяца.
- Различать шаблон серии и её экземпляры: хранить стабильный `recurrenceSeriesId`, правило и плановую дату следующего экземпляра так, чтобы редактирование одного экземпляра не меняло прошлые задачи.
- Решить, какие поля копируются при создании следующего экземпляра: заголовок, описание, приоритет, проект/секция и родительская задача. Не копировать статус завершения, историю комментариев и идентификатор задачи.

### 2. Доменная логика

- В `packages/domain` добавить чистую функцию вычисления следующей плановой даты для каждого типа правила.
- Определить расчёт по календарным датам пользователя, без зависимости от времени запуска сервера и локальной временной зоны сервера.
- Обработать конец месяца, високосный год, переход года, неверные значения и повторное выполнение операции.
- Добавить unit-тесты на обычные случаи и границы календаря; зафиксировать формат даты и часовой пояс в контракте.

### 3. Схема базы и миграция

- Добавить nullable-поля правила повтора, идентификатора серии и состояния серии (либо эквивалентную отдельную таблицу серий, если это проще поддерживать).
- Добавить ограничения БД для допустимых значений и согласованности полей правила.
- Сгенерировать Drizzle-миграцию; существующие задачи должны остаться обычными задачами без правила.
- Проверить индексы, используемые для поиска серии и защиты от повторного создания экземпляра.

### 4. Backend API и атомарное завершение

- Расширить Zod-схемы создания и обновления задачи валидацией правила и требования даты.
- Возвращать правило серии в ответах API и экспортах, где это уместно.
- При завершении задачи в одной транзакции обновлять её статус и создавать следующий экземпляр, если серия активна.
- Сделать операцию идемпотентной: повторный запрос завершения или повтор после сетевой ошибки не должен создать несколько следующих экземпляров. Использовать уникальное ограничение/ключ экземпляра серии и обработать конфликт транзакционно.
- Поддержать остановку серии и определить поведение удаления задачи/серии.
- Добавить API-тесты: создание, редактирование, завершение, повтор запроса, права доступа и транзакционный отказ.

### 5. Интерфейс

- Добавить поле повтора в формы создания и редактирования задачи; отключать или очищать его при удалении даты согласно согласованному UX.
- Показать краткое описание правила в деталях задачи и в списках там, где оно полезно.
- Дать возможность изменить правило для будущих экземпляров либо остановить серию; явно обозначить область действия изменения.
- При оптимистическом завершении обновлять текущую задачу и показывать следующий экземпляр после ответа сервера; не создавать клиентом независимую копию, способную разойтись с сервером.
- Добавить компонентные тесты на настройку, показ правила и состояние после завершения.

### 6. Проверка сквозного сценария и выпуск

- Добавить Playwright-сценарии: создать ежедневную задачу, завершить её и убедиться, что следующий экземпляр появился с правильной датой; проверить остановку серии.
- Проверить месячные даты на 29–31 числа и выполнение просроченной задачи.
- Обновить документацию пользователя, описание API и `MEMORY.md`.
- Выполнить обязательный для проекта цикл: `pnpm test`, `pnpm test:e2e`, затем `pnpm build`; исправить все регрессии до выпуска.

## Основные риски

- **Повторные запросы** могут породить дубли. Нужны транзакция и ограничение уникальности, а не только проверка в UI.
- **Календарь и часовые пояса** дают расхождения на границе суток. Домен должен работать с календарной датой задачи и согласованным часовым поясом пользователя.
- **Редактирование серии** может неожиданно менять прошлые задачи. Контракт должен чётко ограничивать изменение текущим и будущими экземплярами.
- **Повторяющиеся подзадачи** создают вопросы о повторении дерева и связях с родителем. В первой версии лучше не поддерживать повторение подзадач, пока не определено отдельное поведение.

## Критерии готовности первой версии

- Пользователь может задать ежедневное, еженедельное или ежемесячное правило для задачи с датой.
- Завершение создаёт ровно один следующий незавершённый экземпляр с ожидаемой датой и данными.
- Повторная отправка запроса не создаёт дублей.
- Пропущенные экземпляры не создаются пачкой; месячные короткие периоды обрабатываются предсказуемо.
- Серия может быть остановлена, а существующие экземпляры остаются доступными.
- Domain, API, UI и E2E проверки покрывают правила и граничные случаи.
